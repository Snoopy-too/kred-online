### Model assignment rationale

**Delegate to Haiku 4.5 (Steps 1, 2, 4, 9):** mechanical, pattern-matching work with clear tests and small local edits. Haiku is fast, cheap, and capable enough — the risk of silent drift is low because the tests catch regressions immediately.

**Keep on Opus 4.6 (Steps 3, 5, 6):** these are the load-bearing architectural moves.
- **Step 3** touches the heart of the dual-channel sync — wrong edits desync host/guest silently.
- **Step 5** is the architectural pivot. Getting the split state/dispatch context wiring wrong cascades into every later step.
- **Step 6** involves discriminated-union wire format, version math, and `flushSync`/microtask interaction with React 19. High blast radius.

**Mixed steps:**
- **Step 7:** Opus drives the first provider migration (Roster) to validate the Step 5 template survives contact with a complex slice. After that, Haiku can migrate the remaining providers one-at-a-time using the validated template, with Opus reviewing each subagent result before the commit.
- **Step 8:** Opus drives the reconnect hardening task (`hasHydratedRef`, version resume, retry backoff — these interact with Step 3's sync path). Haiku handles validator authoring, ErrorBoundary boilerplate, and handler wrap-up.

**Why this split pays off:** the Haiku steps are ~60% of the total task count. Running them on Haiku saves significant tokens and wall-clock time while Opus concentrates its budget on the five or six tasks where a subtle wrong call would cost far more to debug than it would to prevent.

**Failure mode to watch for on Haiku steps:** Haiku tends to produce plausible-looking code on hard problems even when it's wrong. The two-stage review in `superpowers:subagent-driven-development` is the safety net — don't skip it. If a Haiku subagent's output *looks* right but you can't immediately articulate *why* it's right, re-dispatch to Opus.

## How the steps build on each other

**Steps 1–2 lay the foundation.** Nothing else depends on them, but everything after benefits:
- Step 1 builds a host↔guest sync test harness. This is the safety net for every subsequent change.
- Step 2 builds a dev-only PerfStore + overlay. It's how later steps *see* whether their change helped.

**Steps 3–4 are the "safe wins."** Low-risk, high-value sync layer fixes and correctness audits that do not depend on the App.tsx breakup:
- Step 3 drops redundant guest subscriptions, fixes the action poll, decouples DB persist from broadcast, and kills `window.__kred_pushState`.
- Step 4 bounds every long-lived collection, codifies phase-cleanup rules in a matrix doc, and asserts subscription stability.

**Step 5 is the first surgical move on architecture.** It introduces the `GameProviders` + `GameStateAggregator` pattern but only migrates one slice (PhaseProvider). This proves the pattern works end-to-end before Step 7 repeats it five times.

**Step 6 ships the wire-format optimizations** that Section 5's test matrix can now protect: delta packets (behind `SYNC_DELTAS`) and the microtask-yield action queue (behind `SYNC_MICROTASK_YIELD`). Both are flagged so they can be reverted with a one-line flip.

**Step 7 is the biggest step.** It migrates the remaining five providers (Roster, Board, Campaign, Challenge, Bureaucracy), removes prop drilling from screens, and shrinks App.tsx to ≤ 500 lines. One provider per commit; sync tests green at every boundary.

**Steps 8–9 are correctness and UX polish.** Step 8 adds two-layer validation, hardens reconnect, and adds error boundaries. Step 9 sweeps UI buttons for double-submit, confirmation, and disabled-state issues.

## Critical invariants (never violate across any step)

1. **All existing tests stay green.** Run the full suite after every task within every step.
2. **3, 4, AND 5 player modes all keep working.** New tests parameterize across all three; dev smoke verifies each.
3. **No schema changes.** `kred_game_states` and `kred_game_actions` columns are fixed.
4. **Host is the source of truth.** Guests emit intentions; host validates, applies, broadcasts.
5. **Wire format is backward-compatible.** Step 6's delta packets ride on top of the same broadcast channel and the same DB snapshot format.
6. **Delta packets stay healthy across provider migrations.** The aggregator's `useMemo` dep array is load-bearing — dropping a dep silently drops state updates.
7. **Instrumentation stays dev-only with zero prod cost.** Tree-shakes out when `PERF_ENABLED === false`.

## Definition-of-done for the full engagement

Pulled from `specs/2026-04-09-multiplayer-perf-hardening-design.md`, §"Acceptance criteria (overall)":

- PerfStore overlay renders without errors in dev; no measurable cost in production builds.
- Sync mock + helpers exist; baseline 10+ tests pass.
- `kred_game_actions` poll fetches incrementally; `processedActionIdsRef.size` is bounded.
- Guest establishes only the broadcast channel + poll fallback (no `postgres_changes` on `kred_game_states`).
- Delta packets on the wire; full snapshot in DB; sync test matrix verifies round-trip equivalence.
- `App.tsx` shrinks to ≤ 500 lines (or the engagement explicitly stops mid-Step-7 with a documented checkpoint).
- All existing tests pass.
- Sync test matrix passes for 3, 4, AND 5 player counts.
- Top-level + per-screen error boundaries exist; auto-rejoin on top-level catch.
- No new Supabase schema migrations are required.
